# Кеш, индексы и производительность

## Кеш карточки курса

| Параметр | Значение |
|---|---|
| Где | память одного процесса API (`api/src/cache/cache.service.ts`). Redis не нужен |
| Что | общая часть карточки курса: название, описание, статус, `version`, категория, преподаватель |
| Ключ | `course:<id>` |
| Срок | 60 секунд |
| Размер | не больше 100 ключей. При переполнении удаляется самый давно использованный |
| Очистка | сразу после успешного `PATCH /courses/:id` |
| Не кешируется | проверка доступа (зачисление студента читается из базы на каждом запросе), число студентов, оценки, результаты, списки, любые личные данные |

- **Права.** Общий ключ хранит только данные, одинаковые для всех, у кого есть доступ к курсу. Права проверяются при каждом запросе, поэтому теплый кеш не откроет курс постороннему или отчисленному. Это проверяет тест `test/integration/cache.spec.ts`.
- **Сбои.** Ошибка кеша не ломает запрос: значение просто читается из MongoDB. Ошибка загрузки (например, 404) в кеш не попадает.
- **Гонка чтения и изменения.** Если чтение началось до изменения курса, а закончилось после, его результат в кеш не записывается (счетчик поколений ключа). Это проверяет unit-тест.
- **Как увидеть.** Заголовок ответа `X-Cache: HIT | MISS` в DevTools → Network при открытии страницы курса.

### Замер с холодным и теплым кешем

Нужны запущенный API (`npm run start:dev`) и демо-данные (`npm run seed`).

```bash
cd api
npm run perf:cache
```

Порядок замера:
1. Изменение курса, кеш очищен.
2. Пять одинаковых чтений: первое — MISS, остальные — HIT.
3. Изменение курса.
4. Чтение: MISS и уже новое название.

Результат записывается в [perf/cache-results.md](perf/cache-results.md).

## Индексы и explain

```bash
cd api
npm run perf:explain
```

Эксперимент работает **только в тестовой базе** (`MONGODB_URI_TEST`) в отдельной коллекции `explain_submissions`:
1. Создается 5000 связанных версий работ: 1 курс × 50 заданий × 100 студентов.
2. Два реальных запроса проекта выполняются с `explain('executionStats')` до индексов и после них.
3. Записываются план (`COLLSCAN` / `IXSCAN`), имя индекса, `docsExamined`, `keysExamined`, `returned` и время.

| Запрос | Где используется | Индекс |
|---|---|---|
| `find({ assignmentId, studentId }).sort({ number: -1 })` | сдача версии: последний номер | `uniq_submission_number` |
| `find({ courseId, submittedAt: { $gte, $lt } }).sort({ submittedAt: 1 })` | отчет и CSV за период | `course_submissions_by_time` |

Результат с реальными цифрами записывается в [perf/explain-results.md](perf/explain-results.md). Если планировщик не выбрал индекс, скрипт так и пишет: ускорение не выдумывается.

## Ограничения объема

- Списки: `limit` до 100 (REST) и до 20 (GraphQL). Работы и история оценок отдаются постранично.
- Отчеты: до 200 заданий и 2000 студентов, факты для report-service — до 5000.
- CSV: поток по курсору, без накопления в памяти.

## Одновременные изменения главного ресурса

| Сценарий | Проверка |
|---|---|
| 5 одновременных сдач одного студента | номера 1..5 без повторов (`concurrency.spec.ts`) |
| две одновременные оценки одной версии | одна запись в `grades`, второй запрос — 409 (`concurrency.spec.ts`) |
| два одновременных зачисления | одно действующее зачисление (`concurrency.spec.ts`) |
| два одновременных `PATCH` курса | один 200, второй 409, чтение после — данные победителя (`cache.spec.ts`) |
